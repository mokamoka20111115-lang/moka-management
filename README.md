# カフェレスト モカ 経営管理

スマートフォンから日々の売上・経費を記録し、月間の経営状況を確認できるWebアプリです。

## iPhoneから使うための公開手順（GitHub Pages）

GitHub Pagesを使えば、公開リポジトリでは無料でこのアプリを公開できます。このリポジトリには、`main`ブランチへ変更が入るたびに自動公開する設定が含まれています。

### 最初の1回だけ行う操作

1. GitHubでこのリポジトリのページを開きます。
2. 上部の **Settings** を押します。見つからない場合は、上部の **…** の中を確認してください。
3. 左側メニューの **Pages** を押します。
4. **Build and deployment** の **Source** で **GitHub Actions** を選びます。
5. この変更のPull Requestを **Merge** して、`main`ブランチに反映します。
6. リポジトリ上部の **Actions** を開き、左側の **GitHub Pages に公開** を選びます。
7. 実行結果が緑色のチェックになるまで1〜3分ほど待ちます。

通常、公開後のURLは次の形式です。

```text
https://あなたのGitHubユーザー名.github.io/moka-management/
```

たとえばユーザー名が `moka-cafe` なら、URLは `https://moka-cafe.github.io/moka-management/` です。正確なURLは **Settings → Pages** の上部にある **Your site is live at**、または成功したActions画面の **deploy** に表示されます。

> リポジトリ名を `moka-management` 以外に変更した場合は、URL末尾もそのリポジトリ名になります。

### iPhoneのホーム画面へ追加

1. iPhoneのSafariで上記URLを開きます。
2. 画面下部の共有ボタン（四角から上向き矢印）を押します。
3. **ホーム画面に追加** を押します。
4. 名前を確認して **追加** を押します。

以後はホーム画面の「モカ経営管理」からアプリのように開けます。

## データ保存について（重要）

入力データはサーバーではなく、開いたSafariの中に保存されます。そのため利用料やデータベース設定は不要ですが、次の点に注意してください。

- Safariの履歴・Webサイトデータを削除すると、入力データも消える可能性があります。
- プライベートブラウズでは使用しないでください。
- 別のiPhoneやパソコンにはデータは自動共有されません。
- GitHub Pagesでリポジトリを公開しても、入力した売上データがGitHub上で公開されることはありません。

この最初のバージョンでは、同じiPhoneのSafariから継続して使う運用を想定しています。

## パソコンでの起動方法


ブラウザで `http://localhost:4173` を開いてください。

## 営業データのバックアップと復元（iPhone）

- 「バックアップ」→件数・日付範囲・各日の金額を確認→「ファイルに保存」→共有画面の「ファイルに保存」を選びます。共有が使えない場合は「ダウンロード」を押してください。JSONが開いたらSafariの共有ボタンから保存できます。保存先にファイルがあることを確認してください。
- 「復元」→「ファイルを選ぶ」でMOKAのJSONを選びます。件数・日付範囲と「日付・金額を確認する」を確認し、同意チェックを入れて「確認して復元する」を押します。ファイルを選んだだけでは上書きしません。
- 復元は追加ではなく全記録の置き換えです。空のバックアップは全記録を空にします。現在の記録を先にファイルへバックアップしてください。
- 復元直前の元データはブラウザ内の `moka-before-restore-v1` にも退避しますが、直近1回分だけです。復元用ファイルの代わりではありません。
- 表示用サンプルはバックアップ対象外です。最初の入力保存時にもサンプルを混入させません。以前のアプリで既に保存された記録は実データかサンプルか自動判別できないため、そのまま保持し注意文を表示します。
- 未対応の形式、不正な日付・金額、日付重複、5MBを超えるファイルは拒否します。ファイル名や拡張子だけでは判定しません。
- Safariまたはホーム画面から、普段データを入力している同じ環境でバックアップしてください。バックアップは暗号化されていないJSONです。自分の「ファイル」等で保管し、Publicリポジトリにアップロードしないでください。

## GoogleログインとFirestore保存

ログイン前は従来どおりこの端末のlocalStorageを利用します。ログイン後は `users/{uid}/entries/{YYYY-MM-DD}` に営業記録を保存します。クラウドが空の場合は空表示になり、サンプルは登録しません。ログインだけでは端末の記録をアップロードしません。

Firebase Web SDK 10.14.1をGoogleの公式CDNから遅延読み込みします。SDKの読み込みに失敗しても、未ログインのローカル機能は使えます。Web設定は公開用です。管理者SDK・サービスアカウント鍵・パスワードは含めていません。

### 公開前にFirebaseコンソールで行うこと

1. Firebaseプロジェクト `moka-management` を開きます。
2. Authentication → 設定 → 承認済みドメインに `mokamoka20111115-lang.github.io` を追加してください。末尾の `/moka-management/` は入れません。
3. Authentication → ログイン方法でGoogleが有効になっていること、サポートメールが設定されていることを確認します。
4. Firestore Database → ルールを開き、このリポジトリの **firestore.rules全体**をコピーして置き換え、「公開」を押します。GitHubにファイルを置くだけではFirebaseのルールは変わりません。本番ルールの公開は、この変更をアプリへ反映する前に行ってください。
5. アプリのPRをマージすると既存GitHub Actionsがテスト・ビルドしGitHub Pagesへ公開します。
6. iPhoneのSafariでログインし、少額の営業記録を保存します。同じGoogleアカウントでPCから開き、同じ値が表示されることを確認します。別アカウントではその記録が表示されないことも確認します。確認用記録を消す場合はバックアップ・復元の置き換え対象を慎重に確認してください。
7. iPhoneのホーム画面からもログイン・保存・ログアウトを確認してください。ポップアップがブロックされた場合は、Safariで同じサイトを開いてログインを試してください。ログインはポップアップ方式で、リダイレクト方式は導入していません。

ルールはGoogle認証済みの本人UIDだけを許可し、日付・金額・項目を検証します。ほかのGoogleアカウントも自分のUID配下は利用できますが、あなたのUID配下にはアクセスできません。アプリ全体を1人専用に制限する設定ではありません。

### 端末の既存データを移行する

1. **ログイン前に**従来の「バックアップ」でこの端末のJSONを「ファイル」へ保存します。
2. Googleでログインし、画面のメールアドレスが移行先のアカウントであることを確認します。
3. 「この端末の記録をクラウドへ移行」を押します。件数・日付範囲・全金額を確認し、サンプルが含まれていないか確認します。
4. 同じ日付で金額が違う記録がある場合は移行を中止します。同じ内容なら取り込み済みとして飛ばします。競合を解消する場合は両方をバックアップしたうえで、通常の営業入力画面から意図した金額へ編集してから再度移行してください。
5. 同意にチェックし「確認して移行する」を押します。保存後にサーバーから読み直して照合します。通信が切れて完了を確認できない場合は、最新データを読み込み、移行を再実行してください。同一データは重複しません。
6. 元の `moka-entries-v1` は削除しません。移行後にログアウトすると元のローカルデータが表示されます。以後のクラウドへの編集はそのローカルデータへ自動反映されないため、保存先表示を確認してください。

### クラウドのバックアップ・復元

ログイン中のバックアップは、サーバーから本人の**全営業データ**を取得してJSONにします。ログイン前の古いJSONも復元可能です。復元はクラウド全記録の置き換えで、全端末へ影響します。内容確認と同意が必要です。

復元前のクラウドデータは `moka-cloud-before-restore-{uid}` にJSONとして退避します。退避が失敗すればクラウドを変更しません。各UIDの直近1回分のみで、端末データ削除に耐えるバックアップではありません。復元前に必ずファイルも保存してください。

### 保存と競合の扱い・初期版の制限

- クラウド操作はオンライン必須です。通信失敗時は入力画面を閉じず金額を残します。入力の下書きはアカウント別にメモリ保持するので、画面を閉じて開き直せます。ただしページ再読み込みやアプリ終了では下書きは失われます。
- 日次保存と日付変更はFirestoreトランザクションで実行します。`users/{uid}/state/current` の更新番号を同じ処理内で進め、別端末の先行更新を検出します。競合の場合は入力を保持し、閉じる→最新データを読み込む→入力を開き直す→内容確認→保存の順に操作します。
- 他端末の変更はアプリを開き直すか「最新データを読み込む」で取得します。常時リアルタイム同期・オフライン編集は未対応です。
- 初期版は営業データが少ない運用を想定して全件取得します。移行・全件復元は1回のトランザクションで変更する営業記録が400件以内の場合に対応し、超過時は変更前に中止します。大規模データの段階的な移行・復元は別途対応が必要です。
- 未ログインでも同じ端末のローカル記録は表示できます。端末を共有する場合は、この挙動と元データが残ることに注意してください。

### 検証範囲

`npm test` は既存の計算・月移動・バックアップ検証に加え、DOMテストダブルによる入力保持・認証切り替え・復元画面の検証と、注入したFirestore APIのテストダブルで保存・移行・復元・競合・通信失敗を検証します。本番Firebaseへ営業データを書き込むテストではありません。

Firebase Rulesのエミュレーターによる実行検証、および本物のGoogle認証・iPhone Safari・ホーム画面での実機確認は、この作業環境では未実施です。Firebaseコンソールでのルール公開と対象端末での確認が必要です。

## iPhoneでGoogleログインが進まない場合

現在のログイン方式はFirebase SDKの `signInWithPopup` です。`authDomain` の `moka-management.firebaseapp.com` はGoogleログインを中継するFirebaseの認証ドメインで、アプリ本体のGitHub Pagesドメインとは異なります。FirestoreのルールはGoogleアカウント選択の前には関係しません。

ログイン準備時に、Firebase SDKの認証ドメイン検証と同じ公開プロジェクト設定APIを読み、公開アプリのホストが承認済みか確認します。未登録・無効なAPIキー・APIのアクセス制限・通信失敗を認証画面へ移動する前に表示します。準備に失敗した場合は設定を直してアプリを再読み込みしてください。ローカル機能は維持します。

ログイン処理中はボタンを無効にし、1つの認証要求だけを実行します。連打で先に開いたポップアップの認証がキャンセルされる問題を防ぎます。エラーは日本語と `auth/...` のコードを表示します。トークン・eventId・認証URLを診断ログとして保存しません。

「The requested action is invalid.」はFirebase認証ページが要求を受け付けられなかった表示で、文言だけで原因は一意に判定できません。今回のコード調査では、アプリが認証URLを独自に作っていたり、Firebase設定値が別の値に書き換わっていたりする問題は見つかっていません。次の順に確認してください。

1. Firebase Authentication → 設定 → 承認済みドメインに `mokamoka20111115-lang.github.io` があることを確認します。`/moka-management/` は入れません。
2. ホーム画面からではなく、Safariの通常タブで公開URLを直接開き、ボタンを1回押します。Safariとホーム画面アプリのログイン状態は共有されない場合があります。
3. アプリ側に表示される `auth/...` のエラーコードを確認します。認証タブにだけエラーが出た場合は、そのタブを閉じてアプリ側のエラーも確認します。
4. 承認済みドメインが正しくても失敗する場合は、GoogleプロバイダのWeb SDK設定、サポートメール、Google OAuthクライアントとAPIキーの制限を確認します。必要な制限だけを正しく設定し、制限を一律に解除しないでください。
5. 追加調査には、Safariでも同じエラーか、認証ページのパスが `/__/auth/handler` か、URLの `authType` が `signInViaPopup` か、`providerId` が `google.com` かを確認します。完全な認証URL、eventId、state、トークンを共有する必要はありません。

### signInWithRedirectに単純変更しない理由

GitHub PagesとFirebase認証ヘルパーが別ドメインのまま `signInWithRedirect` / `getRedirectResult` を追加すると、Safariの第三者ストレージ制限によって、認証後の結果を元のアプリで取得できないことがあります。iPhoneだからという理由で自動的にリダイレクトへ切り替える処理は入れていません。

リダイレクト方式での対応が必要な場合は、Firebase Hostingなどでアプリと認証ヘルパーを同一ドメインにする、または公式のプロキシ/ヘルパー構成へ対応する作業が別途必要です。GitHub Pagesは認証ヘルパーへの動的なリバースプロキシを提供しません。公開先を移す場合は、元のSafariのlocalStorageが別ドメインへ自動的に移らないため、先にJSONバックアップまたはクラウド移行を完了させます。

公式情報：https://firebase.google.com/docs/auth/web/redirect-best-practices

今回の自動テストは、設定検証、ポップアップ開始前のチェック、連打防止、再試行、エラー表示と既存機能をテストダブルで検証します。本物のGoogleログインやiPhone Safari/ホーム画面アプリの認証完了を確認したものではありません。
